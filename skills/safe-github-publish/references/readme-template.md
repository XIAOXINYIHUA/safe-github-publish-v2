# GitHub README 编排指南

目标不是堆装饰，而是让访客在 30 秒内回答三个问题：这是什么、为什么值得尝试、怎样跑起来。只写能从代码、测试、发布记录或真实素材验证的内容。

## 编排顺序

按项目实际情况组织"价值 → 证据 → 行动 → 细节 → 信任"：

1. **价值**：项目名和一句准确描述，避免口号式标题。
2. **证据**：至多一个最有说服力的截图、终端输出、基准图或结果示例。
3. **行动**：最短可执行的安装与使用路径。
4. **细节**：功能、工作原理、配置、兼容性和扩展示例。
5. **信任**：限制、安全边界、贡献方式和已有许可证。

首屏通常只放项目名、一句话、0–4 个可验证 badge 和一个真实证据。默认左对齐；只有项目已有品牌资产时才使用居中的 logo/title 区域。不要加入装饰性横幅、emoji 墙、无效 badge 或与项目无关的引用。

- 3–5 个可验证的关键能力

## 视觉与信息密度

- **Badge**：最多保留真实版本、构建、覆盖率、许可证等可验证状态；同类只留一个。`repo_lint.py` 超过 6 个会警告。
- **截图/GIF**：展示实际界面或结果，必须提供准确 alt 文本；发布前剥离 EXIF。
- **深浅色素材**：已有两套真实图片时用 `<picture>`；不要临时制造：

  ```html
  <picture>
    <source media="(prefers-color-scheme: dark)" srcset="docs/dark.png">
    <img src="docs/light.png" alt="应用主界面">
  </picture>
  ```

- **终端示例**：`console` 代码块展示输入和输出；删去用户名、绝对路径和无关日志。
- **表格**：只用于横向比较；移动端难读的宽表改为列表。
- **目录**：正文超过约 6 个主要章节再添加。
- **折叠**：平台差异、完整配置放 `<details>`，核心步骤保持可见。
- **标题**：任务导向（`Quick start`、`Configuration`）；删除空章节——`repo_lint.py` 会标记。
- **链接**：站内一律相对路径，大小写与目标文件完全一致（GitHub 区分大小写）。

## 快速开始标准

必须是可复制、顺序完整且不含真实凭据的最短成功路径。优先一个主路径，其他平台或包管理器放后文。

```console
$ tool install example
Installed example

$ example run input.txt
Processed 1 file
```

若命令未经实际运行，明确标注前置条件，不伪造成功输出。

## Mermaid 选择

- 架构/数据流 → `flowchart`（4–9 个节点，单向少交叉）
- 请求链路 → `sequenceDiagram`（只留关键交互，不含内部地址/密钥/客户名）
- 生命周期 → `stateDiagram-v2`（状态与转换来自实际实现）
- 实体关系 → `erDiagram`

图表必须解释仅靠段落不易看懂的关系，不能充当装饰。`repo_lint.py` 校验块内有合法图表类型。

## GitHub 原生可视化

- 地理项目：GeoJSON / TopoJSON code block，仅公开或已脱敏坐标。
- 3D 项目：ASCII STL code block，仅允许公开的模型。
- 补充信息：`<details><summary>` 折叠长内容。
- 不依赖任意 JavaScript、iframe 或远程追踪代码制造"交互效果"。

## 质量检查（与 repo_lint 对齐）

- 首屏立即说明用途、对象和下一步；单一一级标题。
- 快速开始章节存在且命令顺序完整、可复制。
- 示例不含真实 token、账户、路径或私人数据。
- 图表来自实际架构并能在 GitHub Markdown 渲染。
- 相对链接全部可达且大小写正确；无空章节、无虚假 badge、无不可验证宣传语。
- 窄屏仍易读：无过宽表格、无超长代码行。
